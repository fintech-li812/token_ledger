# 内控视角下的 tokenledger

## 1. 为什么 AI 成本需要内控

传统内控盯的是人、钱、物的流转，凭证、审批、对账一应俱全。
模型调用是一条新的支出流，它的特点是：**自动化、高频、无单据、事后只剩一个总数**。

于是常见的结果是：月底账单上有一笔钱，但没人能回答四个问题——

1. 这笔钱花在哪个 agent / 哪个项目上？
2. 是谁授权的，额度是多少？
3. 有没有超限，超了之后有没有人知道？
4. 这条记录有没有被改过？

tokenledger 就是把内控的四个动作（**凭证化、授权、对账、审计留痕**）补到这条支出流上。

## 2. 五要素映射（《企业内部控制基本规范》）

| 内控要素 | 在本项目中的落地 |
| --- | --- |
| 内部环境 | 账本即仓库：`tokenledger.toml` 定义环境，凭证内固化 `recorded_by` / `approved_by` 两个职责字段 |
| 风险评估 | 授权凭证定义 agent / 项目 / 期间 / 额度；用量入账时逐笔比对，超限即打 `budget_status=exceeded` |
| 控制活动 | 授权审批、职务分离、连续编号、幂等去重（`dedup_key`）、只增不改（append-only） |
| 信息与沟通 | `query` 明细、`report` 汇总、`export` 交付、`report --exceptions` 例外报告 |
| 内部监督 | `verify` 哈希链审计、`reindex` 账实核对、`reconcile` 外部对账、git 历史形成第二重留痕 |

## 3. 控制目标 → 控制手段 → 穿行测试

穿行测试（walkthrough）就是"从头到尾追一笔业务"，这是审计最常用的手法。

| 控制目标 | 控制手段 | 怎么测（穿行测试） |
| --- | --- | --- |
| 完整性：花掉的每一笔都入账 | `ingest` 按 session+ordinal 逐条解析，凭证号连续无缺号 | 抽一个 session，比对日志里 `token_count` 条数与账本凭证数 |
| 准确性：金额与 token 数正确 | 单价来自配置文件，未定价凭证标记 `unpriced` 而非记 0 | 抽一条凭证手工重算 `input * 单价 + output * 单价` |
| 真实性：记录来源于实际调用 | 凭证带 `source.parser` / `source.file` / `source.sha256` | 按凭证里的文件哈希定位原始日志行 |
| 授权：支出在批准的范围内 | 授权凭证 + `budget_status` | 跑 `tledger budget status`，看执行数与额度 |
| 不可篡改：事后无法改账 | 哈希链（每条凭证含 `prev_hash`）+ git 提交历史 | 手工改一行 JSONL，再跑 `tledger verify`，必须报错 |
| 账实相符：明细账与总账一致 | 明细账（JSONL）为唯一真相，SQLite 仅为派生索引 | 删掉 `index.sqlite` 跑 `tledger reindex`，数字必须一致 |
| 总账核对：分次累加 = 累计值 | 凭证同时保存增量与累计 token，`verify` 逐 session 核对 | 看 `tledger verify --json` 的 `session_totals` 段 |
| 入账前证据：日志在入账前没被改过 | `attest sign` 对源日志做 HMAC-SHA256 并登记；入账时逐文件核对，状态写进凭证 | 签名后往日志里追加一条用量再 `ingest`：该凭证应标 `changed`，`verify` 退出码 3 |

## 4. 关键设计取舍

- **明细账为准，索引可弃**：`ledger/*.jsonl` 是唯一真相，SQLite 只是查询加速。任何索引损坏都能 `reindex` 重建，
  这是"账实核对"能成立的前提。
- **异常不阻断，只标记**：超预算的凭证照样入账，但打上 `exceeded` 标记。
  内控的目的是**让异常可见**，而不是把异常藏起来或直接丢掉。
- **不猜价格**：单价必须由使用方自己核对后填入配置。未定价的凭证永远不会被当成 0 元来处理。
- **只增不改**：账本不提供 update / delete 命令。冲正只能通过追加反向凭证实现，这正是会计上的红字冲销。
- **印章不与账本同放**：签名密钥默认落在用户配置目录，不进账本仓库。
  否则能改账的人也能顺手重签一份"干净"的来源证明。
- **本地优先**：解析本机 agent 日志，不上传任何数据；哈希链与 git 让"谁在什么时候写了什么"可回溯。

## 5. 已知边界

- 哈希链证明"入账之后没被改过"；入账**之前**的完整性由 `attest` 补上：
  日志在签名后被改动，状态会变成 `changed`，并让审计直接不通过。
- 但 `attest` 仍不是不可否认性证明：密钥由运维者持有，它证明的是"签名之后没变过"，
  证明不了"持有密钥的那台机器自己没有造假"。真正的非否认需要 agent 侧持有独立私钥，属于 Roadmap。
- 账本以**记账顺序**串成哈希链，不要求事件时间严格单调（乱序补录历史日志是正常业务）。
- 未内置任何厂商账单的解析规则，对账用通用 CSV 列名，具体列名以 `reconcile --help` 为准。
- 凭证上的 `budget.status` 是**入账当时**的判定快照。账本只增不改，所以事后补签的授权不会回头改写历史凭证；
  要看实时执行情况请用 `tledger budget status`（它是实时重算的，两者不一致本身就有信息量）。
- 授权应当**先于**支出签发。事后补签虽然能看实时额度，但那些凭证的入账快照仍然是 `unbudgeted`，
  这本身就是一条值得复核的例外。
